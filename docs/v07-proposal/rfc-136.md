# Open RFC #136 — Toward 1.0

0.7 is planned as the last large breaking release before 1.0 ([compatibility promise](./README.md#compatibility-promise)). Nothing is released yet, and these **five design choices** especially benefit from downstream experience before the API freezes:

### 1. Pedals derived from CC64

Code that builds scores—such as a tokenizer decoding pedal tokens—now writes control change 64 pairs (`ControlChange(t, 64, 127)` / `ControlChange(end, 64, 0)`) instead of appending `Pedal` objects. **Is that workable, or is a helper for writing pedals needed?**

### 2. In-place mutators vs returning transforms

Mutating transforms (`sort`, `shift_*`) return `None`, while element-dropping/copying transforms (`filtered`, `clip`, `adjust_time`) return new objects. **In downstream pipelines, which operations rely on mutating through shared references versus returning an independent copy?**

### 3. Strict MIDI parsing by default

Readers reject MIDI data bytes above 127 unless `strict=False` is passed (replacing `sanitize_data=True`). **Which datasets or workflows in practice require byte clamping?**

### 4. Typing and `EventList[Note[Tick]]`

Annotations use `Score[Tick]` and a single generic `EventList[Note[Tick]]` (with `EventList.from_numpy(Note, ...)`) instead of separate `NoteList[Tick]`, `TempoList[Tick]`, `TextEventList[Tick]`, etc. **Does this fit how you annotate and construct event lists, and do you need dedicated `TypeIs` narrowing helpers beyond `if score.ttype is Tick:`?**

### 5. Default `Note` velocity = `64`

Top-level `symusic.Note` previously required `velocity` (while `core.NoteTick` defaulted to `0`). The plan defaults `velocity=64` (`0x40`, MIDI 1.0 recommended default, matching `mido` and `muspy`). **Does `velocity=64` fit downstream usage, or should `velocity` remain required?**
